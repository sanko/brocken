=head1 NAME

Brocken::Builder - Build script for the Brocken distribution

=head1 SYNOPSIS

    # Normally ./Build is generated for you by Build.PL
    perl Build.PL
    ./Build
    ./Build test
    ./Build install
    ./Build realclean

=head1 DESCRIPTION

The distribution's build script. It is a L<Module::Builder> subclass, so C<Build.PL> is the usual C<Module::Builder>
one-liner and the C<./Build> file is generated from the C<Build_PL> method here. It is based on
L<Module::Build::Tiny> and is mostly a transcription of that module into a C<core::class>.

The point of interest to anyone hacking on the distribution is C<step_build>, because it is what puts the
documentation where users can reach it. See L</"WHAT GETS INSTALLED">.

=head1 ACTIONS

The action is a constructor parameter, and C<Build> dispatches by method name, so C<action =E<gt> 'test'> calls
C<step_test> and an unknown action dies with C<No such action 'E<lt>nameE<gt>'>.

=over

=item C<build>

C<step_build>. Generates any C<.PL> files, then copies the modules, documentation, scripts, and shared data into
C<blib>. This is what C<./Build> with no action does.

=item C<test>

C<step_test>. Builds first if C<blib> does not exist, then runs every C<.t> under C<t/> through
L<TAP::Harness::Env> and returns whether there were errors. C<blib/arch> and C<blib/lib> are put on C<@INC> and
on C<PERL5LIB>, so the tests see the built distribution rather than C<lib>. C<--jobs> and C<--verbose> are passed
through to the harness, and colour is enabled only when C<STDOUT> is a terminal.

=item C<install>

C<step_install>. Builds if needed, then hands the file map to L<ExtUtils::Install> with the paths from
C<ExtUtils::InstallPaths>.

=item C<clean>

C<step_clean>. Removes C<blib> and C<temp>.

=item C<realclean>

C<step_realclean>. Removes C<blib>, C<temp>, C<Build>, C<_build_params>, C<MYMETA.yml>, and C<MYMETA.json>.

=back

=head1 WHAT GETS INSTALLED

C<step_build> walks four trees and builds a file map, all relative to C<blib>:

=over

=item C<lib>, for C<.pm> and C<.pod>

Both are found and mapped, and the two are passed to C<pm_to_blib> together. The C<.pod> lookup is a separate find
from the C<.pm> one, which means every module can have a sibling C<.pod> and both are installed; the C<.pm> is
placed at C<blib/lib/...> and its documentation alongside it. A module with no C<.pod> is still installed, so the
two are independent rather than paired.

=item C<script>, for programs

Every file under C<script> is copied to C<blib/script>, its C<#!> line is rewritten to the C<perl> that is running
the build, and it is made executable. Files already ending in C<.pod> are pulled out first and go into C<blib/lib>
instead, so a script can carry its own documentation.

=item C<share> and C<module-share>

Everything under C<share> lands in C<blib/lib/auto/share/dist/> followed by the distribution name, and everything
under C<module-share> in C<blib/lib/auto/share/module>. These are the two share conventions, and they are the
mechanism for installing files that are not Perl at all.

=back

If one of these directories does not exist the walk finds nothing and continues, so a distribution that ships no
C<script> or no share data does not need the directory to be present. Brocken currently ships none of the three.

=head1 GENERATED FILES

Any C<.PL> file under C<lib> is treated as a generator: it is run as a script with the corresponding C<.pm> path as
its argument, and a non-zero exit is fatal. This exists so a module can compute part of itself at build time, and
the distribution currently has no C<.PL> files, so the loop does nothing.

C<Build_PL> writes the C<Build> script itself, with the C<perl> path, this class name, and the option list
substituted in, and makes it executable. It also writes C<_build_params> as JSON, which is how the options given to
C<Build.PL> are carried across to the C<./Build> invocation. If the distribution metadata has an
C<x_dynamic_prereqs> custom key, it is evaluated at this point with L<CPAN::Requirements::Dynamic> and merged into
the effective prerequisites before C<MYMETA.json> is written, and the metadata is saved with
C<dynamic_config> turned off so that the result is fixed once and for all.

=head1 PARAMETERS

=head2 C<action( )>

The action name, C<build> by default. See L</"ACTIONS">.

=head2 C<meta( )>

A reader, a L<CPAN::Meta> loaded from C<META.json> at construction. A distribution without a C<META.json> will fail
here rather than later.

=head2 Install-related parameters

C<install_base>, C<installdirs>, C<uninst>, C<install_paths>, C<destdir>, and C<prefix> are passed to
L<ExtUtils::Install> and L<ExtUtils::InstallPaths>. C<install_paths> defaults to an C<ExtUtils::InstallPaths>
built from the distribution name. Their values run through C<detildefy> in C<get_arguments>, so a shell-quoted
value from C<PERL_MB_OPT> is handled.

=head2 C<verbose( )>, C<dry_run( )>, C<jobs( )>, C<pureperl( )>

C<verbose> is passed to the file operations and to the test harness, C<jobs> to the harness, and C<dry_run> to
C<ExtUtils::Install>. C<pureperl> is accepted and not used, since nothing here builds anything to be
architecture-dependent.

=head1 STATUS

Expect breakage. This is the standard L<Module::Builder> skeleton, and it carries that module's assumptions, which
is worth knowing before changing it.

C<build> and C<test> gate on C<-d 'blib'>, so a C<blib> that exists but is incomplete is not rebuilt and the test
step will run against stale files. Removing C<blib> is the way to force a clean build.

The C<.pm>, C<.pod>, and C<script> walks are three separate finds and the script walk is a match-everything
C<qr/(?:)/> that is then filtered, which means the script list briefly contains C<.pod> files that are moved out by
C<delete> while the hash is iterated over the keys of a copy. It works, but it is fragile in a way that will bite
anyone who adds a second kind of file to C<script>.

The share directories are looked up by name derived from C<$meta-E<gt>name>, so a distribution whose metadata name
contains characters that are not path-safe will produce a path that is not what the share convention expects.

C<pureperl> is dead. The C<arch> directory is created and never populated, because C<step_build> copies everything
into C<blib/lib> and C<blib/arch> gets no files from this script.

C<Build> calls C<exit> on the result of the step rather than returning it, so C<Build> is the last thing that runs
in the process and its return value is not a usable status.
